# Agent Note: ShotGo 合并与数据库发布由用户执行

Status: implemented

[English](2026-08-24-shotgo-user-owned-merges-and-database-rollout.md) | 中文

## 问题

ShotGo 由多人共同开发，并使用多个 Git Remote。从未同步的本地基线创建分支，可能遗漏其他开发者已经接受的改动；自动执行本地合并，则会移除用户最终审核点。数据库变更的风险更大且更难恢复，因为应用测试本身无法证明生产语句命中了预期 Schema、行数据和发布时间窗口。

## 决策

每项可独立评审的 ShotGo 改动都先切换到用户指定的基线，确认工作区可安全切换，再通过 `git pull --ff-only` 从该分支已配置的远程仓库完成快进更新。Agent 只在更新完成后创建新的范围化开发分支，禁止直接在 `master` 或 `release/*` 开发。出现非快进或冲突时停止并请求用户决定，不重写共享历史。

Agent 在开发分支完成适用检查并准备提交，但绝不把提交合并到 `master` 或 `release/*`，包括本地合并。交接信息包含基线、开发分支、待合并提交、准确检查、警告，以及是否执行了另行授权的推送或部署。合并决定和操作由用户负责。

每项数据库或数据表修改都采用两步审核。Agent 先提供准确 Migration 或 SQL、目标、预期 Schema 或行数据影响、兼容性、验证查询以及备份或回滚步骤，不执行 DDL 或修改性 DML。用户审核或调整语句，并手动应用到必须部署的本地数据库；随后 Agent 可以针对该本地状态执行只读验证和应用测试。

生产数据库操作始终由用户执行。本地验收通过后只产出准确语句集合或从本地复制到生产环境的步骤，以及验证查询；Agent 不执行生产 DDL、DML、Migration、导入或复制。任何数据库修改流程要越过语句预览阶段，都必须取得第二次明确确认；本地验证不完整时，禁止交付生产操作方案。

## 曾考虑的替代方案

**直接从当前本地 `master` 创建分支。** 否决，因为本地状态无法证明已经包含其他开发者的远程改动。

**测试通过后由 Agent 执行合并。** 否决，因为测试通过只能提供技术证据，不能替代用户对分支历史、审核时机和发布范围的批准。

**本地应用测试通过后直接在生产执行 Migration。** 否决，因为该方式合并了代码与数据发布权限，跳过准确语句审核，并让恢复依赖未经验证的生产操作。

**允许 Agent 在语句获批后应用到生产。** 否决，因为即使技术验证完成，用户仍要求生产数据库执行和本地到生产复制保持手动操作。

## 后果

每项改动都从最新共享基线开始，并以可评审分支结束，而不会隐式合并。数据库工作增加一次语句预览和本地验证周期，但生产修改保留明确的人工执行点、准确语句、回滚信息和变更后查询。Agent 仍可在已授权范围内执行只读诊断与本地应用测试，但不能据此推定具有合并或生产写入权限。
