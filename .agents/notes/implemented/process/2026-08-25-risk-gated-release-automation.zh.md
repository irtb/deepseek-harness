# Agent Note: 风险门禁下的自动发布

Status: implemented

[English](2026-08-25-risk-gated-release-automation.md) | 中文

## 问题

ShotGo 需要快速完成仓库与生产流程，同时不能让范围有限的功能修改破坏共享 Agent、服务、契约、后台任务或数据。强制二次确认和只允许人工执行生产操作会增加重复暂停，但本身不能证明修改 A 对 B、C 安全。

流程仍需区分已请求的实现工作与生产修改授权。数据库和数据表变更需要特别醒目的风险分析，因为 Schema 与数据兼容性故障可能影响共用同一数据库的多个应用。

## 决策

每项可独立评审的工作都从已同步的指定基线新建分支，并且只处理一个事项。实现前，Agent 把需求行为映射到共享模块、契约、调用方、后台任务、兄弟 Agent、服务和数据路径。验证必须覆盖需求行为和每个已识别使用方；任何必需检查被跳过、无法执行、不稳定或失败，都会阻止合并或发布。

合并、推送、部署和数据库执行不设置常驻二次确认门禁。用户当前请求包含某项操作时，Agent 可以在适用检查和安全前提通过后完成该操作。仅要求开发、诊断、审查或状态报告时，不授权生产修改。远程移动、非预期分支、破坏性目标不明确或范围变化仍会让执行停止，而不会扩大权限。

部署必须记录准确提交或不可变产物、受影响服务、健康检查和回滚结果，并且不得重启无关服务。数据库和数据表工作必须重点报告准确操作、受影响 Schema、表、行、依赖服务与代码路径、兼容性风险、备份、回滚和验证。本地或预发布环境可用时先完成验证，在生产执行最小范围的已授权操作，然后立即验证 Schema、数据和依赖服务不变量。

## 曾考虑的替代方案

**每次发布序列前强制二次确认。** 不予采用，因为已经披露、测试并位于当前请求范围内的操作，不会仅凭重复批准就变得更安全。远程和范围检查仍然强制执行。

**所有生产部署和数据库操作都要求用户手动执行。** 不予采用，因为执行主体不能替代自动检查、不可变身份、备份、回滚和变更后验证。Agent 只能在当前任务授权内执行。

**把所有开发请求视为生产授权。** 不予采用，因为实现与生产修改仍是不同范围。用户必须请求发布或部署，但不要求使用特殊的重复确认语句。

**只测试直接修改的功能。** 不予采用，因为 ShotGo 共用运行时组件、契约、队列、模型配置和数据库状态。每个已识别使用方都需要与风险相称的回归证据。

## 后果

常规的已授权发布无需人为确认暂停即可继续，自动化可以包含生产部署和数据库执行。Agent 必须在实现前投入更多工作识别受影响使用方，并保留可审计的风险、身份、验证和回滚证据。

授权或目标不明确时操作会停止，但不会仅因缺少规定的确认措辞而停止。即使自动执行，数据库风险提示也必须保持醒目；分析时已识别的 B、C 回归路径尚未测试时，本次修改仍未完成。
