# Agent Note: 人工确认的生产发布

Status: implemented

[English](2026-08-25-human-confirmed-production-release.md) | 中文

## 问题

ShotGo 开发需要自动化验证和由 Agent 执行仓库操作，同时不能让最初的开发请求自动获得生产发布权限。失败或已经过时的测试结果不得触发合并，生产分支推送也不得授权 Agent 操作生产服务器。

## 决策

每项可独立评审的工作都从已同步的指定基线新建分支。所有适用的自动检查通过后，Agent 先核查远程分支拓扑，再报告已评审的源代码、集成分支、生产分支、生产远程仓库和准确结果，然后停止。用户针对这些标识发出的一次二次明确确认会授权完整 Git 发布序列：合并并推送集成分支，再把完全相同的结果提升并推送到生产分支。多个 Git 操作不会产生额外确认门禁。

如果指定分支不可用或在确认后移动，Agent 会停止，而不会自行选择替代目标。它会同步开发分支、重新执行受影响的检查，并因为已确认标识不再有效而提交新的完整方案。必需检查被跳过、无法执行、不稳定或失败时，均禁止获得合并授权。

生产分支推送是 Agent 操作发布流程的终点。Agent 提供与结果提交 SHA 绑定的准确生产服务器部署、验证和回滚命令，用户手动执行这些命令。数据库和数据表修改继续遵循独立的语句预览、本地验证、确认以及由用户执行生产操作的流程。

## 曾考虑的替代方案

**所有分支始终由用户手动合并。** 不予采用，因为用户希望在审阅测试证据并发出第二次确认后，由 Agent 完成机械性的合并和生产分支推送。

**分别确认集成分支与生产分支推送。** 不予采用，因为用户批准的是一条已完整披露的发布序列，而不是逐项批准每个机械性的 Git 操作。

**把开发请求视为发布授权。** 不予采用，因为这会移除已验证代码与生产分支修改之间有意设置的确认节点。

**允许 Agent 在推送生产分支后部署。** 不予采用，因为仓库发布与生产服务器修改具有不同的风险和恢复属性。生产操作人员继续控制服务器拉取、构建、Migration、重启和部署命令。

## 后果

该流程在验证后只有一个明确的发布确认暂停点。远程竞态会使该方案失效，而不会静默扩大授权；未变化的方案不会索要多次确认。作为交换，Agent 可以完成确定性的仓库操作，却不会获得发布未经评审代码或操作生产基础设施的长期权限。

每次交接都会记录已评审源代码、目标、远程仓库、检查结果、确认和结果 SHA。部署指令保持可审计、可复制，执行权仍由人工掌握。
